## 1. Product Vision & Value Proposition

### 1.1 Глобальная цель

> **Максимизировать пропускную способность по ЛЮДЯМ** (человеко-поток, люди/час), а не по автомобилям; **снизить суммарную задержку** и время холостого простоя; **минимизировать выбросы CO₂**; гарантировать **беспрепятственный проезд экстренных служб**.

Ключевой продуктовый сдвиг относительно классической АСУДД: стандартные контроллеры оптимизируют **поток ТС (vehicle/pcu)**. Наша система вводит метрику **PERSON-THROUGHPUT (PT)** и считает пассажиров через коэффициенты загрузки, что смещает приоритет в пользу общественного транспорта и пешеходов.

### 1.2 Как мы «считаем людей», а не машины

Видение камеры даёт **тип** объекта, а не число людей внутри. Число пассажиров оценивается **статистической моделью загрузки** (occupancy coefficients), которые калибруются локально по периодическим замерным обследованиям (сплошной подсчёт пассажиров в автобусах, выборочный опрос водителей).

#### Таблица 1.1 — Базовые коэффициенты вместимости (настраиваются per-intersection)

| Класс объекта | Коэффициент загрузки (чел.) | Источник/комментарий |
|---|---|---|
| Легковой автомобиль | **1,20** (ближнее место ~1.15–1.35) | В среднем 1.2–1.6 в РФ/ЕС; по умолчанию консервативно 1.2 |
| Такси / каршеринг | **1,25** | Чуть выше легкового |
| Мотоцикл/мопед | **1,00** | Один водитель |
| Микроавтобус (маршрутка) | **12–16** | По заполняемости маршрута (модель времени суток) |
| Автобус | **25–45** | Калибруется по расписанию и спросу; время пик/внепик |
| Троллейбус | **30–50** | |
| Грузовой (фура/лёгкий) | **1,00** | Водитель |
| Спецтранспорт (экстренный) | ∞ (приоритет, метрика не считается) | Блокирующий вес в решении |
| Пешеходы (переход) | **1 × N** (прямой подсчёт) | Точный счёт трекером зоны выжидания |
| Велосипед/СИМ | **1,00** | |

**Формула метрики решения:**

```
PT_фазы = Σ( count_vehicle_class × occupancy_class ) + Σ pedestrians

Эффективность фазы = PT_фазы / Δt_фазы   [люди/сек]
```

Система выбирает фазу с **максимальной предельной эффективностью** (marginal person-throughput per second of additional green), а не максимальным числом машин.

### 1.3 Ценность для города

- **Транспортные коридоры:** автобус с 40 пассажирами на фазе «весит» как 33 легковых — общественный транспорт получает приоритет без весового штрафа для пешеходов.
- **Пешеходная справедливость:** скопление у перехода инициирует приглашение пешеходной фазы в пределах max-time ожидания (инженерный предел — до 90–120 сек, см. п. 4.2).
- **Экстренные службы:** гарантированное прерывание цикла за время ≤ 2–3 сек от детекции.
- **Экономика города:** сокращение простоев снижает износ покрытия, расход топлива и сопутствующее загрязнение.

### 1.4 Экологический эффект (минимальная модель выбросов)

Выбросы холостого хода (idling) аппроксимируются линейно:

```
E_CO2 [кг/час фазы] = Σ_idle_vehicles × idle_rate_class [кг CO₂/час на ТС]

Типичные оценки (близкие к реальным):
  • Легковой (бензин, ~1.6л):  ~1,8–2,6 кг CO₂/час на холостом ходу
  • Грузовик/автобус (диз):   ~5,5–8,5 кг CO₂/час
```

Целевой эффект MVP на одном перекрёстке (оценочно): **−15…−25 % суммарного времени холостого простоя** и пропорциональное снижение CO₂ в локальном периметре. Вложенность несложная, но результаты нужно подтверждать на пилоте (см. п. 7, KPI).

### 1.5 Продуктовое позиционирование

- **Парадокс «дешёвого edge»:** RPi 4 (≈ $55–60) — достаточная вычислительная база для версионируемой встраиваемой CV-системы класса «одно устройство на перекрёсток». Это в разы дешевле серверной инференции и не требует кабельных ВОЛС к ЦОД.
- **Принцип «советник, а не замена»:** система НЕ заменяет сертифицированный светофорный контроллер. Она **рекомендует и в ограниченном режиме подаёт сигналы вызова** (call), оставаясь безопасно отключаемой при любом отказе (глава 5). Это снижает барьер согласования с ГИБДД и владельцем объекта.
- **Целевые сегменты:** муниципалитеты, региональные операторы АСУДД, концессии умных городов, девелоперы (тротуар/перекрёсток у ТЦ).

### 2.2 Пояснения к ключевым позициям

- **Почему 2 камеры, а не 1:** одна камера не покрывает все подходы перекрёстка без сильных искажений. На MVP — 2 камеры на 2 смежных/противоположных подхода; масштабирование до 4 — добавление CSI-мультиплексора или второй RPi-мультиплексора.
- **AS-IS ограничение RPi 4:** 1 CSI-порт. Для 2 камер используем: (а) USB-камеры с MJPEG для второй; (б) CSI-мультиплексор (переключение — не одновременная работа); (в) правильно — **вторая камера через USB-видеозахват** (gitty/usb). Рекомендованная схема: CSI V2.1 (основная) + USB-камера 1080p MJPEG (второй подход). Это отражено в BOM (поз. 2 + поз. 3/4).
- **Терморежим:** активное охлаждение включается >65 °C ядра. Для уличного кейса обязателен вентиляторный приток с фильтром — без него CV-нагрузка ведёт к троттлингу CPU (снижение fps) и ложно неустойчивой работе.
- **Мощности:** RPi 4 при максимальной нагрузке до 7,5–10 Вт (без учёта периферии) — отсюда БП 5 В/6 А минимум в индустриальном исполнении.

## 3. Архитектура программного обеспечения и стек

### 3.1 Принципы архитектуры

- **Монолитное edge-приложение с чёткими модулями** (не микро-микросервисы: на RPi контейнеризация даёт оверхед, но изоляция модулей — через процессы/service-контракты).
- **Determinism:** цепочка принятия решения — детерминированные (не нейросетевые) алгоритмы с фиксированными таймингами. Нейросеть только в слое восприятия.
- **Graceful degradation:** каждый сенсорный слой имеет режим «нет данных → fallback» (глава 5).

**Классы детекции (7):**
- `passenger_car`, `bus`, `truck`, `motorcycle`, `bicycle`, `pedestrian`, `emergency_vehicle`

**Обучение спецтранспорта:** спецкласс `emergency_vehicle` (скорая, пожарная, полиция) обучается на датасете из ~3–5 тыс. размеченных кадров (реальные фото + синтетические вариации: разметка «А03», мигалки, ночной режим, искажённый ракурс). Финальная модель — 2-стадийная: первая стадия — общий детектор, вторая (лёгкий классификатор cropped) — подтверждение «экстренности». Возможен **аудио-канал (сирена)** как enhancement (п.4.1).

### 3.5 Профили производительности

| Режим | fps | Задержка «кадр→решение» | Когда |
|---|---|---|---|
| **NOMINAL** | 15 fps | ~110–140 мс | Штатно, обе камеры |
| **TURBO (Coral/Edge TPU)** | 30–45 fps | ~40–60 мс | Требует аппаратного ускорителя |
| **LOW-POWER/FALLBACK** | 5–8 fps | ~250 мс | Перегрев/энергосбережение, CB=EV priorities снижены |

> На RPi 4 без ускорителя 4 камеры одновременно необрабатываемы → при масштабировании либо 2×RPi, либо Coral на мост.

### 3.6 Запуск и изоляция

- Всё приложение — **один systemd unit** (`smarttraffic.service`), pigpio — отдельный демон.
- Контейнеризация (docker-compose на balenaOS) рекомендуется только на этапе пилота для атомарных OTA. На MVP — нативный запуск с read-only root и варированием mnt для логов.

## 4. Функциональные требования (Core Features)

### 4.1 Модуль детекции объектов

**FR-1.1 Детекция классов:** система распознаёт ≥ **7 классов** (см. 3.4) с точностью: mAP@0.5 ≥ **0.85** на собственных тест-сетах; recall по пешеходам ≥ 0.9 (безопасность).

**FR-1.2 Подсчёт зон:** виртуальные зоны/линии (JSON-конфиг): stop-line zones, waiting zones (пешеходы), approach zones. Счётчики:
- `N_waiting_veh[class][lane]` — ТС в очереди до стоп-линии;
- `N_peds_waiting` — пешеходы в зоне выжидания перехода;
- `N_pass` — поток за зелёную фазу.

**FR-1.3 Трекинг:** ассоциация объектов между кадрами (ID), счётчик по пересечению, фильтрация ложных срабатываний устойчивым треком ≥2 кадров. Подсчёт людей — устойчивыми траекториями (не детекциями одиночных кадров).

**FR-1.4 Экстренный транспорт:**
- Детекция `emergency_vehicle` с confirm-порогом (2 смежных кадра) → событие `EV_DETECTED`;
- Аудио-канал (опционально, см. ниже): YAMNet-подобный классификатор сирены → только как **подтверждение**, никогда как единственный источник;
- Гео-подтверждение (спутник/сервер АСУДД): корреляция трека с координатами объекта, если доступна телеметрия.

**FR-1.5 Режимы съёмки:** день/сумерки/ночь — авто-переключение по уровню освещённости; фикс-экспозиция при антиблике, IR-подсветка (по желанию) на ночной период. Оценка качества кадра (п.5.2).

### 4.2 Алгоритм принятия решений (decision engine)

Движок — **иерархический конечный автомат (HFSM)** + **жадный планировщик** сцены. Формальные состояния:

```
IDLE → EVALUATE_CANDIDATES → (amber_transition) → ACTIVE_PHASE → ...
        │                        ▲
        ▼                        └── EV_HOLD / FAILSAFE
   FALLBACK_TIMER (деградация)   FAULT (только разрешённые безопасные фазы)
```

**Псевдокод высокого уровня:**

```
loop (каждые T_cycle = 100–200 мс):
  scene = aggregate(S1..S2): {counts_by_class, peds, ev_flags, health}

  # 1) Приоритет №1 — экстренный, прерывает немедленно
  if ev_confirmed(any cam) and scene.time_since_ev >= EV_RESPONSE_MAX(2.0 s):
      request_priority_phase(align_ev_approach); EV_HOLD until cleared
      nop → # полный preemption

  # 2) Пешеходный вызов (справедливость)
  if peds_waiting >= PED_CALL_THRESHOLD(3) or ped_wait_time >= PED_MAX_WAIT(90 s):
      schedule_ped_phase; reset timer

  # 3) Основной выбор: максимальная PT
  candidates = feasible_phases(MIN_GREEN, MAX_GREEN, safety_constraints)
  for ph in candidates:
      pt(ph)  = Σ count_class[ph] * occupancy[class] + Σ peds[ph]
      bound(ph)= pt(ph) / Δt_green(ph)          # люди/сек добавленного зелёного
  phase = argmax(bound);  extend = (bound(phase) > EXTEND_RATIO * current_bound_ref)

  # 4) Защита от «голодания»
  if phase_current == phase:  comply with MAX_GREEN; else switch (amber)

  # 5) Корректировки
  if no_demand_on_phase: skip phase (red-light run protection), respect MIN via central
```

**Ключевые параметры (конфиг YAML, тайминги в мс):**

| Параметр | Значение по умолчанию | Пояснение |
|---|---|---|
| `T_cycle` (детектор) | 200 мс | Частота пересчёта решения |
| `MIN_GREEN` (авто) | 15 с | Минимум безопасного зелёного |
| `MAX_GREEN` (авто) | 60 с | Предел непрерывного зелёного |
| `MIN_GREEN_PED` | 6 с | Пешеход (по ГОСТ/ПДД, включ. WALK) |
| `PED_MAX_WAIT` | 90 с | Предел ожидания пешехода в очереди |
| `PED_CALL_THRESHOLD` | 3 пешехода | Порог инициации пешеходной фазы |
| `AMBER` (жёлтый) | 3 с (пример) | По местным нормативам |
| `ALL_RED_CLEARANCE` | 2–4 с | Очистка перекрёстка |
| `EV_RESPONSE_MAX` | 2,0 с | От детекции EV до прерывания цикла |
| `EV_HOLD` | до проезда + 8 с | Удержание выделенной фазы |
| `EXTEND_RATIO` | 1,15 | Порог для продления текущей фазы |
| `SAFETY_LOCKOUT` | per-phase, 1–2 цикла | Задержка после смены фазы |

**Приоритет фазы (обобщённо):** `EV_HOLD > PED_SCHEDULE > PT-greedy > FIXED_TIMER(fallback)`.

### 4.3 Модуль управления (передача сигнала на светофор)

**FR-3.1 Два режима управляющего выхода:**

| Режим | Что коммутирует | Способ | Статус |
|---|---|---|---|
| **A. Прототип (стол)** | Светофорные LED-макеты | GPIO → 4-канальное реле (поз. BOM 12) | MVP v1.0 |
| **B. Реальный перекрёсток (pilot)** | Входы штатного контроллера (dry contact «call vehicle», «call ped», фазы) | SSR (поз. 13) → изолированные контакты → входы контроллера | v2.0 (после согласования) |

**FR-3.2 Контракт с контроллером (режим B):**
- Система подаёт **вызовы фаз (phase calls)** и **продление (extension)** по контактам, синхронно с сетью контроллера. ВСЕ тайминги и безопасные состояния (красный+жёлтый и т.д.) остаются в сертифицированном контроллере.
- **Fail-safe:** при потере связи с контроллером / отсутствии ACK — «тихий отказ»: все передачи прекращаются, контроллер уходит в штатный таймерный цикл.
- Поддерживаемые интерфейсы контроллеров: контакты входных клеммников 24 В DC (оптопара SSR), либо последовательный протокол (опционально, по сервисному API производителя, напр. NPT-МАКРОД, УСДК.02 и т.п.).

**FR-3.3 Логика выходов (prototype):**
- Таблица соответствия бит реле ↔ цвет/фаза: `R1=Красный MA`, `R2=Зелёный MA`, `R3=Красный MB`, `R4=Зелёный MB`, жёлтый = композитный короткий импульс на R_x.
- Пиг-пио обеспечивает детерминированные переключения timestamped; все переходы через amber + clearance.

**FR-3.4 Журнал событий:** каждое переключение фазы, решение планировщика, EV-событие, health-флаг записываются в локальную БД/sqlite + реплицируются в cloud (глава 6).

## 5. Нефункциональные требования и отказоустойчивость

### 5.1 Требования по производительности и латентности

| Метрика | Требование | Измеритель |
|---|---|---|
| Задержка «кадр→переключение» (glass-to-actuator) | **≤ 300 мс** | энд-ту-энд |
| Задержка «микроскопический детект → решение» | **≤ 150 мс** | |
| Задержка «решение → контакт реле» | **≤ 50 мс** | pigpio, вывод |
| Джиттер переключения | **±5 мс** | |
| Интервал детекции | ≥ 10–15 fps (NOMINAL) | |
| Непрерывная доступность | **≥ 99,9 %** (с деградацией) | uptime |
| MTBF модуля | ≥ 15 000 ч | без сервисного вмешательства |

### 5.2 Отказоустойчивость: матрица отказов и деградации

| Сценарий отказа | Диагностика | Реакция (fallback) | Состояние |
|---|---|---|---|
| **Камера залеплена снегом/грязью** | 1) SNR/Entropy кадра; 2) детектор CV-«liveness» (GLCM contrast); 3) отсутствие треков длит. время | Обогрев (термокожух, поз.5) → если >N cек анализ: пометка канала DEAD → **переход канала в перекрёстке на фиксированные тайминги**, уведомление | `CAM_DEGRADED` → `CAM_FAIL` |
| **RPi зависла (hung)** | Аппаратный сторожевой таймер (ext. WDT / raspberry PI watchdog + pigpio) | Принудительный reboot; при повторных (≥2 в 10 мин) — **аппаратный bypass**: реле «обход» (поз.14) переводит контроллер в **штатный таймерный режим** без RPi | `CORE_FAIL` |
| **Потеря электропитания** | UPS + ИК-сигнал потери | Плавный переход на АКБ → систематический **graceful shutdown** (сохранение состояния, flush логов), при восстановлении — auto-start | `PWR_EVENT` |
| **Потеря интернет-связи** | ping/health-probe, MQTT keepalive | Местный контур работает автономно; логи и метрики **буферизуются** (QoS1/2 очередь) → отправка после восстановления (глава 6) | `NET_DEGRADED` |
| **Ложное срабатывание EV** | Sorted multi-source confirm (видео + audio + geo) | Игнор, фиксация в журнал; порог динамически корректируется | `EV_FALSE` |
| **Перегрев процессора** | термодатчики CPU, вентилятор PWM | Троттлинг → переход в LOW-POWER (fps ниже), предотвращение thermal shutdown | `THERMAL_DEGRADED` |
| **Отказ SSD/SD** | SMART, write-fail плата | 2-я SD высокого endurance; переключение на RAM-логирование в последней инстанции | `STORAGE_DEGRADED` |
| **Сбой контроллера светофора** | отсутствие ACK от входов | Все выходы перекрыты (SSR = разомкнуты), контроллер сам переходит в безопасный таймер, алёрт в cloud | `CTRL_FAIL` |

**Принцип:** **система «советник»** никогда не блокирует штатный контроллер. При любом неподтверждённом сигнале — входы в «тихое» состояние.

### 5.3 Безопасность (первый приоритет)

- Ни одна смена фазы **никогда** не выполняется без прохождения amber + all-red clearance (даже при EV преемпции).
- Внутренние ограничения `MIN_GREEN`/`MAX_ALLOWED_GREEN` жёстко заданы в конфиге и не поддаются soft-изменению во время работы (подписанный конфиг, CRC).
- Управление доступом: SSH-ключи, запрет пароля, дампирование VPN tunnel для Cloud.
- Криптографические обновления: подпись артефактов OTA.

### 5.4 Журналирование и диагностика

- Локально: sqlite + rotated text log (WAL); телеметрия health: CPU, RAM, temp, fps, per-module status.
- Remote: метрики → cloud (глава 6), Sentry-агент для загрузки исключений (опц.).
- «Чёрный ящик»: циклический буфер последних N=600 с видео-моментов (subsample 1 fps) для следственного анализа спорных ситуаций.

## 6. Edge-to-Cloud интеграция (опционально)

### 6.1 Цель и модель

Обмен метриками, событиями и командной диагностикой центральным сервером города/оператора АСУДД. **Критичность:** edge работает автономно; cloud — надзор, накопление данных, OTA, аналитика, корреляция между перекрёстками.

### 6.2 Протоколы и транспорт

| Канал | Протокол | Уровень/применение |
|---|---|---|
| Телеметрия/события | **MQTT over TLS** (port 8883), QoS1 (события), QoS0 (метрики) | Брокер центра (EMQX/HiveMQ → Kafka) |
| Хранение/бэкап | **HTTPS/REST** | Бульк-выгрузка логов, видеофрагментов |
| OTA | balena/Mender (или `apt`-генерируемые deb) + подписанные артефакты | Атомарное обновление с rollback |

**Формат полезной нагрузки:** **Protobuf** (нативное двоичное) или **CBOR** — в 4–6 раз компактнее JSON. Alt: JSON-схема для отладки.

**Пример события (Protobuf) `IntersectionEvent`:**
```protobuf
message IntersectionEvent {
  string intersection_id = 1;
  string device_id       = 2;
  int64  ts_ms           = 3;   // UNIX ms UTC
  enum Type { PHASE_SWITCH=0; EV_DETECTED=1; FAULT=2; HEALTH=3; COUNTER=4; }
  Type type              = 4;
  string phase_id        = 5;
  int32  peds_waiting    = 6;
  map<string,uint32> veh_counts = 7;   // class -> count
  float  persons_per_hour = 8;
  string payload         = 9;   // detail JSON
}
```

### 6.3 Буферизация при потере связи

- Локальная **очередь (disk-бэктед)** событий с TTL = 30 дней;
- QoS1/2 MQTT + подтверждения; при восстановлении — флаш очереди с корректным порядком `ts_ms`.

### 6.4 Командная плоскость (Cloud→Edge)

- **Конфигурация:** мелкие параметры (коэффициенты, пороги) — по каналу `cfg/<id>` с версионированием; изменяются только при `ACTIVE_STATE=IDLE` в безопасном окне.
- **OTA:** атомарный переход на новую прошивку с автоматическим rollback при провале health-check.
- **Draw-up (эвент-ручка):** экстренная команда «принудительная фаза» только авторизованным оператором с двухфакторным подтверждением, в канале с jitter-защитой.

### 6.5 Схема развёртывания Cloud (reference)

```
[Edge RPi x N] --MQTT/TLS--> [MQTT Broker (EMQX)] --> [Kafka] --> [Time-series DB (InfluxDB)] 
                                                        |--> [Analytics (Spark/Grafana)] 
                                                        --> [Alerts (Opsgenie/Telegram)]
                                                        --> [CDC] --> [Data Lake / MinIO]
```

## 7. Пошаговый Roadmap реализации

|---|---|

**DoD:** 72 ч непрерывной работы с автоматическими fallback; отказ любой камеры не останавливает систему; журнал «чёрного ящика» корректен.

### 7.3 **MVP v2.0 — «Пилот на реальном перекрёстке»** (Weeks 14–24; после согласований)
- Замена выходов реле на SSR + сухие контакты к штатному контроллеру (режим B, п.4.3).

- Калибровка коэффициентов загрузки по фактическим данным.
- A/B-сравнение с фиксированным таймером (базовый сценарий — метрики PT, CO₂, средняя задержка).

**DoD:** KPI-замер по 2 неделям пилота: **PT↑ ≥ 10 %**, задержка −10…−20 %, время простоя −15…−25 %, 0 инцидентов безопасности; заключение о согласовании.
